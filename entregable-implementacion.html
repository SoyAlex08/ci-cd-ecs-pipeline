1. Objetivo y alcance

Este entregable valida que la arquitectura propuesta en el modulo de diseno (Semana 11, "arquitectura-ecommerce-cloud") se puede llevar a una implementacion real, funcional y segura en AWS. El diseno original incluye piezas como CloudFront/WAF, ElastiCache, SQS, Cognito y SES; para esta entrega se acoto el alcance a los 5 requisitos puntuales que pide la rubrica: red y balanceador, app en contenedores, base de datos gestionada, pipeline CI/CD, y logs/alertas basicas. Las piezas fuera de alcance quedan documentadas como trabajo futuro en la seccion 7.

3. Mapeo de requisitos a lo implementado

RequisitoComo se cumplio
Redes, subredes, balanceadores VPC con 2 subredes publicas (para el ALB y las tareas ECS) y 2 subredes privadas (para RDS) en distintas zonas de disponibilidad. Application Load Balancer internet-facing con target group tipo ip y health check en /health.

Pipeline CI/CD GitHub Actions: cada push a main construye la imagen, la sube a ECR, renderiza la Task Definition (inyectando la conexion a la BD desde GitHub Secrets) y actualiza el servicio ECS, esperando a que quede estable.
Logs y alertas basicas Logs de los contenedores en CloudWatch Logs. 4 alarmas de CloudWatch (CPU de ECS, hosts unhealthy en el ALB, CPU y espacio libre de RDS) notificando por correo via un topico SNS.

4. Seguridad

  • Security groups en cascada: internet solo puede hablarle al ALB (puerto 80); el ALB es el unico que puede hablarle a las tareas ECS (puerto 8080); y las tareas ECS son las unicas que pueden hablarle a RDS (puerto 3306). Ningun recurso de computo o base de datos tiene una regla de entrada abierta a 0.0.0.0/0.
  • Base de datos sin acceso publico: a diferencia del modulo anterior de RDS (donde la base era publica y se restringia por IP), aqui PubliclyAccessible=false y vive en subredes sin ruta a internet.
  • Sin credenciales en el codigo: la password de la base de datos nunca se escribe en el repositorio. Se genero localmente, se guardo como secreto cifrado en GitHub Actions (DB_HOST, DB_NAME, DB_USER, DB_PASSWORD) y el pipeline la inyecta como variable de entorno de la tarea al desplegar.
  • Limitacion aceptada: el usuario IAM de este curso no tiene permisos sobre Secrets Manager ni SSM Parameter Store, que serian la forma mas segura de manejar este secreto (con rotacion y sin que quede visible en la Task Definition). Queda documentado como el primer punto a mejorar si se dispusiera de esos permisos.
  • Autenticacion del pipeline sin llaves estaticas: GitHub Actions asume un rol IAM via OIDC (github-actions-ecs-deploy), sin access keys guardadas como secreto.
  • Contenedor sin privilegios de root: la imagen Docker corre la app con un usuario sin privilegios (appuser), no como root. Como consecuencia, el contenedor escucha en el puerto 8080 (no privilegiado) en vez del 80: un usuario sin privilegios no puede abrir puertos por debajo de 1024. El ALB sigue exponiendo el 80 hacia internet y reenvia al 8080 del contenedor.

Estimado total: menos de $1 USD por cada hora que se deje corriendo. Por eso se incluye infra/teardown.sh para apagar todo apenas se termine de validar/entregar.

7. Diferencias respecto al diseno completo de Semana 11 (trabajo futuro)

  • CloudFront + WAF: no se implemento; el ALB queda expuesto directo. Para produccion se agregaria un CDN con WAF delante del ALB.
  • ElastiCache (Redis): no incluido; en esta version de bajo trafico no hace falta cache para sesion/carrito.
  • SQS + Lambda para ordenes asincronas: no incluido en este MVP; el modulo de Lambda (lambda-api-demo) ya demostro esa pieza por separado.
  • Cognito y SES: no incluidos; no hay flujo de registro/login ni envio de correos en esta version funcional.
  • RDS Multi-AZ: se uso single-AZ para bajar el costo del MVP; el diseno de Semana 11 ya justifica por que Multi-AZ conviene quando haya trafico real.
  • NAT Gateway: no se uso; las tareas ECS estan en subred publica con IP publica en vez de subred privada con NAT, para no sumar ~$32/mes de costo fijo. La app sigue sin quedar expuesta directamente porque el security group solo acepta trafico del ALB.

8. Conclusion

Se logro llevar el diseno de Semana 11 a una implementacion real y verificable en AWS, cumpliendo los 5 requisitos pedidos con decisiones de seguridad concretas (base de datos privada, security groups en cascada, sin credenciales en el codigo) y documentando de forma explicita las dos limitaciones tecnicas encontradas en el camino: la ausencia de Secrets Manager/SSM en la cuenta del curso, y el recorte de alcance frente al diseno completo de e-commerce para mantener el costo y la complejidad dentro de lo que pide esta entrega.
